# CLAUDE.md

## Project purpose

This repo is the submission for **SPD Challenge 2026** (Trường ĐH Khoa học Tự nhiên, ĐHQG-HCM), a 360-minute hackathon. The task: build a prototype **Team-Matching** system that automatically forms an optimal team from a mock candidate pool under multivariate constraints.

- **Application context (decided):** a hackathon/project team-matching platform. Users register (name + hard/soft skills + languages), then either host a project (each with named **roles**, each role carrying its own required tech stack, manual or AI-suggested, team-size limit) or find a team (see which specific open roles across all projects match their skills, filterable by skill gap). See `README.md` for the full feature list.
- Full brief: `topic.pdf` at repo root (source of truth for the mandatory requirements below).

## Mandatory functional requirements

Do not drop any of these — they are graded against a live demo, not just code review.

**Candidate data**
- ≥20 mock candidate profiles, JSON or LocalStorage (no real backend/DB required).
- A candidate may satisfy multiple skills/roles at once — never assume a 1:1 person↔skill relationship.
- No filtering or scoring on sensitive attributes (ethnicity, religion, political views) — in any code path, ever.

**Recommendation algorithm**
- Must output ≥1 valid team whenever one exists. A team is valid iff:
  1. No person repeated within the team.
  2. Team size respects the configured limit.
  3. The team covers 100% of the required skills.
  4. All additional constraints are satisfied.
- Any solving approach is allowed (filter, scoring, combinatorics, graph, AI model, ...) — no specific algorithm is mandated.

**Output / explanation**
- The result must show: which requirements are met, role allocation (who covers what), and a plain-language explanation of why the chosen team is optimal.

**Stability & error handling**
- Live changes to candidates or constraints must immediately invalidate results that no longer qualify, and recompute.
- When no valid team exists, the system MUST clearly report which capability/condition is missing.
- Never: fabricate candidate data, repeat a member, infinite-loop, throw an unhandled/"undefined" error, or render a blank screen.

**Judged core flow** (must work end-to-end at all times):
set goal + constraints → browse candidates → trigger team suggestion → view explanation report → adjust constraints and see live recompute → verify graceful "no valid solution" handling.

Demo video (≤3 min) must be able to show all of the above.

## Architecture (source/)

- `source/src/components/` — `Header`, `UserMenu`, `NotificationBell`, `ChatDrawer` (persistent top-right edge tab — positioned to align with `LeftSidebar`'s toggle, not vertically centered — collapsible drawer: group list → messages, with a back button), `LeftSidebar` (collapsible, four list sections: my projects (hosted, `ownerId === currentUser.id`), projects joined (accepted member, owner excluded to avoid duplicating the first section), projects followed, people followed), `ThemeToggle` (horizontal switch, CSS-driven icons — see below), `LanguageToggle`, `Logo` (inline SVG mark, also duplicated as static markup in `app/icon.svg` for the favicon — keep both in sync if the design changes), `Avatar`, `UserLink` (wraps a name in a link to `/users/[id]`), `FollowButton` (shared between the public profile page and project detail page), `icons.tsx` (hand-rolled inline SVGs used instead of emoji throughout), `ProjectCard`/`ProjectBrowser`, `ui/RoleEditor.tsx` (add/edit/remove a project's roles, each with a name + `HardSkillInput` for that role's tech stack — used by both `/projects/new` and the owner view of `/projects/[id]`), plus `ui/Primitives.tsx` and `ui/SkillPickers.tsx`.
- `source/src/lib/` — `store.ts` (reactive LocalStorage data layer: users/projects/requests/chatMessages/notifications/follows, via `useSyncExternalStore`), `matching.ts` (team-formation engine, role-aware — see below), `auth.ts` (client-side SHA-256 password hashing — mock auth only, see below), `slug.ts` (derives a username suggestion from a Vietnamese display name — diacritics-stripped, not guaranteed collision-free, check `isUsernameTaken` before using it), `i18n.ts` (EN/VI dictionary + language store, default `"vi"`), `uiStore.ts` (non-persisted UI state: chat drawer open/view/active-project, left sidebar open/collapsed).
- `source/src/data/` — hard-skill taxonomy, 30 seeded mock candidates (name + username + location + GitHub URL + a realistic 6-7 skill tech stack sized to their role + 2-3 languages), 12 seeded mock projects (Vietnamese, spanning all 6 categories, each with 1-3 named roles carrying their own required skills).
- `source/src/types/` — shared TS types (`UserProfile` (has `followedBy`, `githubUrl`, `languages: LanguageId[]`), `Project` (has `followedBy`), `ProjectRole`, `TeamRequest` (has optional `roleId`), `ChatMessage`, `AppNotification`, `MatchResult`, `RoleAssignment`, etc.). `SOFT_SKILLS` has 10 entries (see below). `LANGUAGES`/`LanguageId` is a separate 8-entry taxonomy (english, vietnamese, korean, japanese, chinese, french, german, spanish) for spoken/written languages — distinct from `hardSkills` (free-text tech stack) and `softSkills`; picked via `ui/SkillPickers.tsx`'s `LanguagePicker` (same chip-toggle pattern as `SoftSkillPicker`) on `/register` and `/profile/edit`, and shown as badges on `/users/[id]`. `projectRequiredSkills(project)` derives the flat deduped skill list from a project's roles when something just needs the union, not the per-role breakdown.
- State is client-side only (no backend, except the one OpenAI proxy route) — constraint changes trigger near-instant recompute. Because there's no server-side data, SSR'd HTML always shows an empty/not-found shell before client hydration reads LocalStorage — expected, not a bug.
- **Store schema changes require bumping `STORAGE_KEY` in `store.ts`** (currently `hackmatch:db:v7`) — old LocalStorage data won't have new required fields (e.g. `UserProfile.followedBy`/`Project.followedBy` replacing the old `UserProfile.likedBy`, or the newer `UserProfile.languages`), and there's no migration path. Bumping the key just reseeds fresh, which is fine for a demo app. `normalizeUser`/`normalizeProject` in `store.ts` also backfill missing fields defensively (e.g. `languages: u.languages ?? []`) so stale partial data from a version bump doesn't throw.

### Follow, not like

`UserProfile.likedBy` was replaced with `followedBy` on both `UserProfile` and `Project` — following is symmetric across people and projects now. `toggleFollowUser`/`toggleFollowProject` in `store.ts`, a shared `components/FollowButton.tsx` (used on the public profile page and the project detail page), and `projectsFollowedBy(db, userId)` (mirrors `projectsForParticipant`) for the `LeftSidebar`'s "Projects followed" list. If a future session is tempted to add a separate "like" feature back in, don't — extend follow instead; there should be exactly one follow/interest primitive per entity type.

### AI role planning (`/api/extract-skills`)

**The team size drives the role count, not the AI.** The New Project form sets team size *before* the AI-assist button (order matters — it's positioned right after the repo/hackathon link field), and sends it as `roleCount` in the request body. The endpoint's system prompt is told the count is already fixed and must name exactly that many roles, then split required skills per role — it must not dump one flat skill list into every role, and it does not get to choose the count itself (that was the previous, now-superseded design). It returns `{ roles: {name, requiredSkills}[], suggestedSoftSkills }`. The New Project page's AI-assist button **replaces** the current role editor state with the AI's roles (not merges). `MAX_ROLES` (10, matching the team-size field's max) and `MIN_ROLES` (1) clamp a malformed/missing `roleCount`; `MAX_SKILLS_PER_ROLE` (6) bounds each role's skill list defensively.

### Roles model (replaces the old flat `requiredHardSkills`)

`Project.roles: ProjectRole[]` — each role is `{ id, name, requiredSkills }`. This is the core mental model now: a project isn't "a list of skills," it's a set of named seats, each needing its own tech stack. Four matching-engine entry points in `lib/matching.ts` build on this:

- **`findTeam({ project, candidates, mustIncludeUserId? })`** — bounded combinatorial search (unchanged safety caps) over the flat union of role skills, then `assignRoles`/`toRoleAssignments` greedily assign the found team to specific roles (most-constrained role first) for the explanation. Still used for the project owner's "Suggested team" panel, but now scoped to only the project's *open* roles and a candidate pool that excludes already-accepted members — it stopped ignoring the confirmed roster.
- **`assignTeamToRoles(team, roles)`** — no search, just assigns a fixed set of people (e.g. already-accepted members) to roles. Used to compute the "Current team" panel on `/projects/[id]` and the Recruit tab's role-fill check.
- **`findOpenRoleOpportunities(user, projects, requests, allUsers)`** — the engine behind `/find-team`'s "Opportunities for me" tab. For every project the user doesn't own, for every role not yet fully covered by an accepted member, if the user's skills overlap that role at all, reports `{ matchedSkills, missingSkills, gap }`. No search/backtracking (linear scan, trivially bounded).
- **`rankCandidatesForRole(role, candidates)`** — the recruiter-facing mirror of the above, behind `/find-team`'s "Recruit" tab **and** the owner-only "Potential participants" card on `/projects/[id]` (below "Suggested team"), which reuses this same function per open role so both surfaces share one ranking algorithm rather than duplicating it. Given one role, ranks the whole candidate pool by skill overlap, excluding zero-overlap candidates. Also a linear scan — deliberately not a search, since there's no "valid team" question here, just relevance ranking.

`/find-team`'s gap filter (fully matched / missing 1 / missing 2 / missing 3+) filters the opportunities list client-side by `gap`. `TeamRequest.roleId` (optional) records which role a request/invite targets.

### Requests flow both ways: applications and invites

`TeamRequest.direction` is `"candidate_to_project"` (a candidate applying — via `/find-team`'s Opportunities tab or the role dropdown on `/projects/[id]`) or `"project_to_candidate"` (an owner inviting — via `/find-team`'s Recruit tab, or the "Potential participants" card directly on `/projects/[id]`). **Whoever didn't initiate the request is the one who accepts/rejects it** — this is the part most likely to get inverted by accident:
- Applications: the project owner accepts/rejects, on `/projects/[id]`'s "Join requests" card. `/my-requests` shows the candidate's own applications as read-only status badges.
- Invites: the *candidate* accepts/rejects, on `/my-requests`. `/projects/[id]`'s "Join requests" card shows pending invites as a read-only "Awaiting response" badge — the owner sent it, they don't also approve it.

`store.ts`'s `addRequest`/`updateRequestStatus` branch notifications on `direction` accordingly (`request_received`/`request_accepted`/`request_rejected` for applications; `invite_received`/`invite_accepted`/`invite_rejected` for invites — six `NotificationType` values total). If you add a new UI surface that lists requests, always branch on `direction` before deciding who gets action buttons — don't assume "pending = show accept/reject to whoever's looking at it."

### Two framework quirks already hit once — don't reintroduce them

1. **`<html>` needs `suppressHydrationWarning`.** A `beforeInteractive` boot script mutates its class (theme) before hydration — a legitimate, expected divergence from server-rendered markup that this attribute is React's documented escape hatch for. Don't remove it while "fixing" a hydration warning; that's what caused one originally.
2. **The theme boot script is a plain native `<script>` rendered inside a literal `<head>` in `layout.tsx` — deliberately NOT `next/script`.** `next/script`'s `strategy="beforeInteractive"` matched the official docs exactly but still threw "Encountered a script tag while rendering React component" in dev on this Next.js/React combo (16.3.0 / 19.2.8) — a likely framework-version quirk (see the `AGENTS.md` warning about breaking changes vs. training data). If you touch this script, keep it a native `<script>`; don't "fix" it back to `next/script` without verifying the warning is actually gone.
3. **Any icon/visual that depends on client-only state (theme, etc.) must not branch in JS between differently-shaped elements** (e.g. `dark ? <MoonIcon/> : <SunIcon/>`). That caused a real hydration mismatch (server always renders the light-mode branch, client can render dark). The fix pattern used throughout (`ThemeToggle`): render *both* elements unconditionally and let a static Tailwind `dark:` class pick which is visible — zero JS branching, zero mismatch risk. Follow this pattern for any future theme-dependent icon/visual.

## i18n scope (important: partial coverage by design)

`lib/i18n.ts` provides an EN/VI dictionary + toggle, defaulting to Vietnamese. Coverage spans nav, auth actions, page headings, form field labels, buttons, empty states, badges/status text, and category/soft-skill labels across every page and component. Deliberately **not** translated: the matching engine's generated explanation sentences (`lib/matching.ts`'s `reason` strings), client-side form-validation error messages, and project body copy (which is itself Vietnamese seed *data* entered by users, not UI chrome — translating user-generated content is out of scope for a UI language toggle). If asked to extend coverage further, add keys to both `vi`/`en` blocks in `DICT` and call `useT()` (or `t()` passed down, per `ExternalLinkButton` in the project detail page) in the target component — don't introduce a second i18n mechanism, and don't forget category/soft-skill labels are looked up as `` `category.${id}` ``/`` `soft.${id}` `` rather than via the old `projectCategoryLabel`/`softSkillLabel` helpers (removed — they're dead code once everything routes through `t()`).

## Mock auth (important: not real security)

Login is by **username** (not display name) + password. Every seeded mock candidate has username = their given name, lowercase, diacritics stripped (see `lib/slug.ts`), and password `12345678`; registered users pick their own username + password (≥8 chars). Passwords are SHA-256-hashed client-side before being stored in LocalStorage (`lib/auth.ts`) — this guards nothing an attacker with browser access couldn't already read, since there's no backend. Treat this as UX polish, not an access-control boundary, and don't let a future session upgrade it to imply real security without adding an actual backend first.
